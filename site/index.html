The problem

Browser GPU work is hard to profile — and impossible to measure exactly.

Frame timing drifts run to run, and the web platform never exposes true VRAM residency. Without a repeatable, machine-readable signal, an agent (or a CI job) can’t tell whether a change actually helped.

Noisy, unrepeatable

Eyeballing FPS in devtools is subjective. Small regressions hide inside frame-time jitter you can’t reproduce.

VRAM is invisible

WebGPU/WebGL2 never report exact GPU residency. You’re guessing at texture and buffer footprints.

Not machine-readable

Screenshots and console tables can’t be diffed. Agents need a verdict and a number they can act on.

One report. A verdict, the numbers, and the fix.

The loop

Baseline, optimize, compare — on repeat.

The skill teaches an agent a four-step loop. The compare step is regression-gated: it exits with code 1 the moment a metric slips, so a “fix” can’t quietly make things worse.

01

doctor

gpu-perf-agent doctor

Confirm the machine and headless Chrome support WebGPU/WebGL2. Always first.

02

baseline

run --auto-instrument

Profile the unmodified page. Capture the verdict, metrics, and warnings.

03

optimize

one targeted change

Apply a single fix for the highest-impact warning — then re-profile.

04

compare

compare --threshold 5

Prove the win. Exit code 1 on regression; check resolvedWarnings.

A fast, direct-CDP runner

The default runner launches Chrome/Chromium itself and talks Chrome DevTools Protocol over a WebSocket — skipping Playwright’s context and driver layers. A Playwright runner stays exported for compatibility.

Persistent server for tight loops

Launch Chrome once with serve and POST repeated jobs to /run. It returns the same report JSON — the fastest path per agent iteration.

Three memory layers, because VRAM residency is hidden

The web platform never exposes exact GPU residency. For deep memory analysis, combine all three.

Declared allocation tracking

--auto-instrument hooks buffer/texture allocations in your app — a deterministic estimate that’s ideal for regression checks.

Chrome trace memory-infra

--trace adds summaries of GPU, frame, and memory-infra events straight from the browser’s own tracing.

Native Instruments (macOS)

xctrace records an Xcode Instruments trace such as Metal System Trace — GPU-driver-level evidence when Chrome’s signals aren’t enough.

The CLI

Five commands. Everything the loop needs.

All five accept --json where it matters, so agents and CI read structured output instead of scraping tables.

doctor
Check WebGPU/WebGL2 support. Run first.
bash
npx gpu-perf-agent doctor
run
Profile a URL or local file into a JSON report.
bash
npx gpu-perf-agent run --url http://localhost:5173 \
  --auto-instrument --samples 5 --out reports/base.json --json
compare
Gate base vs candidate. Exit 1 on regression.
bash
npx gpu-perf-agent compare --base reports/base.json \
  --candidate reports/candidate.json --threshold 5 --json
serve
One persistent Chrome; POST jobs for tight loops.
bash
npx gpu-perf-agent serve --port 9099
# then: POST http://127.0.0.1:9099/run  {"url":"...","samples":5}
xctrace macOS
Record a native Xcode Instruments trace (e.g. Metal System Trace) for GPU-driver-level evidence.
bash
npx gpu-perf-agent xctrace --url http://localhost:5173 \
  --template "Metal System Trace" --time-limit 15s --out reports/metal.trace

Get started

Installed in a minute, looping in five.

Requires Node ≥ 20. The fast runner prefers an installed Chrome/Chromium; if none is found it can fall back to Playwright’s bundled browser.

1

Install the package

Or run it one-off with npx gpu-perf-agent doctor — no install needed.

$npm install -D gpu-perf-agent
2

Run the doctor

Verify your machine and headless Chrome support WebGPU/WebGL2 before profiling.

$npx gpu-perf-agent doctor
3

Capture a baseline

Profile your page with allocation tracking on and machine-readable output.

$npx gpu-perf-agent run --url http://localhost:5173 --auto-instrument --out reports/base.json --json
4

Hand the loop to your agent

Drop SKILL.md into your assistant (see above) and let it baseline, fix, and compare until the verdict is good or excellent.

Reference

Read summary first.

The top-level digest every report opens with — the fields an agent acts on before touching any nested data.

FieldMeaning
verdictOverall health in one word: excellent · good · needs-work · poor.
fpsMean frames per second. High-refresh displays may report 120.
frameTimeMsMean / P95 / MaxFrame-time distribution. A large p95 − mean gap means stutter.
gpuFrameMsMeanMean GPU time per frame when timing hooks are active. > 13 ms means GPU-bound.
jsHeapGrowthMBPerSecJS heap growth rate. > 5 MB/s means allocations in the render loop.
trackedVram{ totalMiB, textureMiB, bufferMiB, textureCount, bufferCount, leakedResources } from --auto-instrument.
slowFrameCountFrames exceeding the slow-frame threshold (default 20 ms).
warningsActionable bottleneck descriptions with recommendations — treat each as a task.
